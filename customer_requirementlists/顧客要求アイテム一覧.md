# 顧客要求アイテム一覧（だんだん動物園入場システム テスト依頼書 より）

## 作成目的
テスト依頼書（`01_だんだん動物園入場システムテスト依頼書_20260426.pdf`）に記載された顧客要求を
機械的に扱える単位（要求アイテム）に分解・構造化する。
後続の「機能モデル生成」「品質モデル生成」「テスト目的生成」フェーズの入力として利用することを想定する。

今後、他のドキュメント（要求仕様書・概要書等）から要求アイテムを追加する際は、
ここに対象ファイルを追記し、各アイテムの「対象ファイル」列で参照すること。

## 作成ルール
- 1スライド（1ページ）に複数の要求が含まれる場合は、要求の意味単位ごとにアイテムを分割する。
- 各アイテムには「対象ファイル（略称）」と「出典ページ番号」を必ず付与し、トレーサビリティを確保する。
- 依頼書に明記されていない／推測を要する内容は「Assumption」として明示する。
- カテゴリは下記5種に分類する。
  - 機能要求：システムの振る舞い・構成変更に関する要求
  - 品質重点要求：「テスト重点項目」として明示された非機能・品質特性
  - スコープ要求：テスト対象/対象外、確認の重み付けに関する要求
  - 背景リスク要求：開発背景に記された将来リスク・状況変化（暗黙の要求）
  - プロセス制約：マイルストーンや成果物提出など、進め方に関する制約

## データ定義
| 列名 | 内容 |
|---|---|
| ID | 要求アイテムの一意な識別子（カテゴリ頭文字+連番） |
| 要求アイテム | 要求内容を簡潔に記述した文 |
| カテゴリ | 上記5分類のいずれか |
| 対象ファイル | 出典ファイル一覧の「略称」を記載。どのドキュメントに基づく要求かを示す |
| 出典ページ | 対象ファイル内の該当ページ番号 |
| 備考/Assumption | 解釈上の注意点、推測した内容、後続工程で確認すべき点 |
| レビューコメント | レビュー担当者記入欄（空欄で提供） |

## レビュー観点
- 各要求アイテムの分類（機能要求/品質重点要求/スコープ要求/背景リスク要求/プロセス制約）が妥当か
- A〜Eの関連付け（例: D3とA3、D1/D2とA1/A2の対応関係）に見落としがないか
- B3・E2のように「Assumption」と判断した項目の解釈が妥当か
- C6・C8のように、顧客が「提案を委ねている」項目を後続フェーズでどう具体化すべきか
- 「対象ファイル」「出典ページ」の記載が、実際のドキュメント該当箇所と一致しているか

## 後続工程での利用方法
- 機能モデル生成: A群（機能要求）を起点に、機能単位への分類・階層化を行う
- 機材モデル生成: A3・D3を起点に、入場ゲート関連の機材依存関係を構造化する
- 品質モデル生成: B群（品質重点要求）を品質特性（信頼性・正確性・効率性等）にマッピングする
- テスト目的生成: C群（スコープ要求）を直接の入力とし、特にC4（重点確認フロー）・C5（差分）・C7（リグレッション）からテスト目的を導出する
- 影響分析: D群（将来リスク）を変更シナリオの種として用い、影響範囲スコアリングのインプットとする
- トレーサビリティ: 各アイテムの「対象ファイル」「出典ページ」を起点に、他のドキュメント（要求仕様書・ハードウェア仕様書等）の該当箇所と突合させる

## Assumption（推測内容）
- B3: 「密回避」要求は新規テスト要求ではなく、既存機能（V01由来）の効果を示す**証跡整理タスク**である可能性が高いと判断した
- E2: V02開発時の補助金申請に伴う成果物提出制約が、V03でも継続するかどうかは依頼書に明記がないため未確定とした

## 不明点（issue.md候補）
- E2の制約がV03テスト設計においても有効か（だんだん動物園側への確認が必要）
- D2（人気動物による予約の早期満枠化）が、今後の機能追加要求（例: 予約枠拡張、優先予約等）に発展する可能性があるか
